# 版本号定版方案（斜月安全管理系统）

## 核心原则

**按变更幅度定版本号，不按日期递增**。一批变更完成后准备发版时一次性定版，按该批内**最高幅度**确定升哪一段。

## 版本号结构（.NET 四段式）

```
1 . 1 . 0 . 0
│   │   │   └── 第4位 微调号：很小、数量少的变更（文案、单点小修、局部优化）
│   │   └────── 第3位 修订号：Bug 修复、界面调整、多个小改进的一批 —— 日常开发的主要版本单位
│   └────────── 第2位 功能号：新增完整功能模块/工具（用户可见新能力；小窗口如使用提示不算，归第3位）
└────────────── 第1位 主版本：重大重构、数据不兼容（老数据无法直接打开）、里程碑定档（如正式版）
```

## 递增规则

1. **一批变更一次性定版**：不按日期、不逐条递增；按该批内最高幅度升段。
2. **递增某段位时，右侧低位全部归零**：
   ```
   1.1.0.0 → 微调一批   → 1.1.0.1
   1.1.0.1 → 修复一批   → 1.1.1.0
   1.1.1.0 → 新功能模块 → 1.2.0.0
   1.2.0.0 → 定档正式版 → 2.0.0.0（如适用）
   ```
3. **幅度判定以"对用户的影响"为准**：用户能感知的新能力 → 功能号；用户感知"坏了/变样了"→ 修订号；几乎无感知的小调整 → 微调号。

## 定版时机与同步点（缺一不可）

定版时机：**一批变更完成、准备制作更新包时**。定版时改齐四处（**数字只改 1 处**）：

1. **根 `Directory.Build.props` 的 `SafetySysVersion`** —— 唯一数字来源；主程序、绿色版启动器（`斜月安全管理系统.exe`）、`Updater.exe` 三者的 `Version` / `AssemblyVersion` / `FileVersion` 全部由它注入。各工程 csproj **不再**单独写版本号（写了会覆盖注入值，等于造出第二个来源）；
2. `MSpirit.SafetySys.Package/AppxManifest.xml` 的 `Identity/@Version` —— MSIX 清单是静态 XML，读不到 MSBuild 属性，必须手工同步（第 4 段按商店要求固定为 0）；
3. `CHANGELOG.md` 对应条目标题（`## [x.y.z.w] - 日期`）；
4. `Views/AboutWindow.xaml.cs` 更新日志 `ChangelogData` 数组的版本标题 + 定版日期（日期格式 `（yyyy-MM-dd）`，与 CHANGELOG 标题行一致）。

README 等文档中的版本号：定档发布时统一更新。

## 与更新包类型的联动

版本号段位作为发包类型的**参考信号**（最终以"依赖库是否变化"为判断，见 dev-conventions 技能）：

| 段位变化 | 发包倾向 | 理由 |
|---|---|---|
| 第 1、2 位 | **全量包** | 新功能/重大变更常伴随依赖库、资源文件变动 |
| 第 3、4 位 | **增量包** | 仅主程序文件变化，依赖未动 |

## 历史归类参考

- `1.0.0.0` = 内测首发（里程碑起点）
- `1.0.1.0` = 修订号（使用提示/关于窗口 + 备份/建表修复 + 测试与打包基建，2026-08-11）
- `1.1.0.0` = 功能号（手机图片传输完整模块 + 托盘多级菜单 + 统一退出管理器，2026-08-12）
- `1.2.0.0` = 功能号（标注与剪裁 + 图片剪裁完整实现 + 数据根保护 + LAN 强化，2026-08-17）

> 注：1.0.0.1 / 1.0.0.2 为按日期逐日递增的旧习惯产物，自方案定稿（2026-08-12）起一律按幅度规则定版。
